# Sailor Conversation & Movement — Design Guide

**Docs:** `docs/Plan_Sailor_Conversation_And_Movement.md`
**Modules:** `fishing_sim/systems/sailor_conversation.py`, `fishing_sim/systems/sailor_motion.py`
**Scope:** Longer, multi-turn conversations (sometimes *much* longer), and believable sailor locomotion/animation. **No SFX in this slice.**

---

## Part A — Conversations That Actually Go Somewhere

The v1 chatter system emits one line, occasionally a two-hander reply. That reads as *ambient noise*. What sells "these are people" is **conversations with a shape**: an opening, a middle that escalates or drifts, and an ending — and the occasional one that runs long enough that you notice it.

### A1. Length tiers

Every conversation declares a **length tier**. The system weights tier selection by context, so long conversations are rare and earned.

| Tier | Turns | Typical use | Base weight |
|---|---|---|---|
| `micro` | 1 | acknowledgements, reactions | 40 |
| `short` | 2–3 | quick exchange | 30 |
| `medium` | 4–6 | working a task together | 18 |
| `long` | 7–12 | night watch, post-haul, tension | 8 |
| `setpiece` | 13+ | after a MAYDAY, a near-sinking, a big catch | 2 |

**Weight modifiers** (multiplied in):

- `+` if both sailors are `idle` and within 3 m of each other.
- `+` if `hour` is night and task load is low (`long` only).
- `+` for `setpiece` if `flooding` just dropped below 0.2, or `radio.choice == "assist"` within the last 10 min, or `catch_aboard` just became true.
- `−` for anything above `short` while `flooding > 0.25` or `sea_state >= 5` (people don't chat mid-emergency).
- `setpiece` cooldown is *global* and long (e.g. 20 min) so they stay special.

### A2. Scripts, not line banks

A conversation is a **script of beats**. Each beat optionally gates on context, optionally names a speaker, and carries its own delivery delay.

```python
@dataclass
class Beat:
    lines: list[str]
    speaker: str | None = None          # None = any participant
    requires: Callable | None = None    # callable(ctx) -> bool; skip beat if False
    weight: float = 1.0                 # for picking this beat vs alternates
    wait: tuple[float, float] = (0.6, 1.8)   # delay before delivery
    tag: str | None = None              # e.g. "escalate", "defuse", "end"

@dataclass
class BeatGroup:
    """Alternate beats that occupy the same narrative slot."""
    options: list[Beat]
    pick: int = 1                       # how many to pick from this group

@dataclass
class ConversationScript:
    id: str
    category: str
    length: str                          # micro/short/medium/long/setpiece
    participants: tuple[int, int]        # (min, max)
    requires: Callable | None
    beats: list[Beat | BeatGroup]
    priority: int = NORMAL
    cooldown: float = 90.0
    interruptible: bool = True
    ends_on: str | None = None           # tag that terminates early
```

`BeatGroup` is the key to *variety inside a script*: a "post-haul" conversation has a fixed opening and closing but three interchangeable middles, so it doesn't play identically twice.

### A3. Runtime: a small state machine

```python
@dataclass
class ActiveConversation:
    script: ConversationScript
    participants: list[str]
    idx: int = 0
    timer: float = 0.0
    next_at: float = 0.0
    paused: bool = False
    log: list[ChatterEvent] = field(default_factory=list)
```

Tick logic:

1. If `paused` and no CRITICAL context has cleared → tick `timer`, do nothing else.
2. When `timer >= next_at`, resolve the current beat (or group), pick a speaker from `participants` who passes `speaker_ok`, emit a `ChatterEvent`, advance `idx`, roll the next `wait`.
3. If `idx` passes the end, or a beat carries `ends_on` matching an earlier tag, **end** the conversation and clear the participants' `in_conversation` flag.
4. If the script is `interruptible` and a CRITICAL context appears (flooding spike, abandon-ship, MAYDAY), set `paused = True`. If the CRITICAL clears within `RESUME_WINDOW` (say 20 s), resume; otherwise abort and let the conversation end with a soft `tag: "cut_short"` beat if one is defined.

**Participants must be co-located.** The system only starts a script if the chosen participants are within `CONVERSATION_RADIUS` (≈3 m) of each other — or if it can path them together first (see Part B, `gather` task). This is what makes conversations feel spatially real.

### A4. Speaker selection and turn-taking

- **Odd/even alternation by default.** Beat 0 → participant A, beat 1 → participant B, etc. Prevents monologues.
- **Affinity bias.** When picking *which* participant speaks, weight by `trust` and by task overlap; two sailors clearing the same gear snag talk more than a helmsman and a bailer.
- **Silence beats.** Some beats have `lines=[]` and a longer `wait` — a pause is part of the rhythm. Don't fear them; a long conversation with a 3-second silence reads as *thinking*, not as a bug.
- **Overlap guard.** A sailor already speaking (or in another conversation) is ineligible.

### A5. Example — a `long` post-flooding conversation

```python
SCRIPT_AFTER_FLOOD = ConversationScript(
    id="after_flood",
    category="aftermath",
    length="long",
    participants=(2, 2),
    requires=lambda c: c.get("flooding", 1.0) < 0.2 and c.get("just_recovered"),
    cooldown=600.0,
    beats=[
        Beat(["That was closer than I like."], tag="open"),
        BeatGroup([
            Beat(["Close enough to taste it."]),
            Beat(["She came back. Boats do, sometimes."]),
            Beat(["I've seen worse. Once."]),
        ]),
        Beat(["You had the pump going before I even got my boots on."]),
        BeatGroup([
            Beat(["Instinct. Nothing clever about it."]),
            Beat(["Somebody had to."]),
        ]),
        Beat([], wait=(2.5, 3.5), tag="silence"),       # deliberate pause
        Beat(["Water's still in the fish room sole."]),
        Beat(["We'll pump it dry before we shoot gear. Or we won't."]),
        BeatGroup([
            Beat(["We will."]),
            Beat(["Not tonight we won't."]),
        ]),
        Beat(["Get some sleep. I'll take the next watch."], tag="close"),
    ],
)

SCRIPT_MAYDAY_SETPIECE = ConversationScript(
    id="mayday_setpiece",
    category="aftermath",
    length="setpiece",
    participants=(2, 3),
    requires=lambda c: c.get("radio_choice") == "assist" and c.get("minutes_since_assist", 999) < 10,
    cooldown=1200.0,
    interruptible=False,
    beats=[...],  # 14+ beats: the call, the decision, the tow, the debrief
)
```

The `setpiece` is deliberately **non-interruptible**: it only fires when the world is calm *because* you did something hard, and letting a fishing task cut it off would waste the payoff.

### A6. Conversation ↔ chatter integration

Keep the existing `SailorChatter` as the *ambient* layer. The conversation system is a **higher tier** that preempts it:

```
if active_conversation: deliver its events; suppress ambient chatter for its participants
else: try to start a conversation (weighted tier roll)
      if none: fall back to ambient chatter
```

Both draw from the same `ChatterEvent` type, so the UI layer doesn't care which produced it.

## Part B — Making Sailors Move Like They Mean It

Right now sailors are points that teleport along A* paths. The goal is: they **accelerate, turn, lean, brace against the roll, get in each other's way, and animate in a way that sells weight** — all without a physics engine or skeletal IK.

### B1. Coordinate space: ship-local, always

Sailors live in **ship-local coordinates**. The world transform applies `heave / pitch / roll` on top. This means:

- A sailor standing at `(3.2, -1.4)` in ship space stays there as the deck moves under them — which is exactly what a person standing on deck does.
- All pathfinding, stations, and collision happen in ship space (2D top-down). Cheap and stable.
- Rendering composes `ship_transform * local_position`, so they *visibly* rise and fall with the hull.

This single decision removes 80% of the "floaty" feeling. People move with the deck, not against it.

### B2. Locomotion model — steering, not snapping

Replace "set position = waypoint" with a velocity integrator. Per sailor:

```python
@dataclass
class MotionState:
    pos: Vec2               # ship-local
    vel: Vec2 = Vec2(0, 0)
    facing: float = 0.0     # radians, smoothed
    max_speed: float = 1.4  # m/s — a brisk walk on a moving deck
    accel: float = 3.0
    decel: float = 4.5
    turn_rate: float = 5.0  # rad/s
    radius: float = 0.35    # personal space
    brace: float = 0.0      # 0..1, how braced against roll
```

Per-tick:

```python
def step(m: MotionState, target: Vec2 | None, dt: float, ctx) -> None:
    if target is None:
        desired = Vec2(0, 0)
    else:
        to_target = target - m.pos
        dist = to_target.length()
        speed = m.max_speed * (1.0 if dist > 0.8 else dist / 0.8)  # arrive
        desired = to_target.normalized() * speed if dist > 1e-3 else Vec2(0, 0)

    # accelerate toward desired
    dv = desired - m.vel
    rate = m.accel if dv.length() > 0 else m.decel
    m.vel += dv.clamped_length(rate * dt)

    # brace slows you down (holding a rail)
    m.vel *= (1.0 - 0.6 * m.brace)

    m.pos += m.vel * dt

    # face movement direction, but turn smoothly
    if m.vel.length() > 0.05:
        want = atan2(m.vel.y, m.vel.x)
        m.facing = approach_angle(m.facing, want, m.turn_rate * dt)
```

**Arrive behavior** (speed falls off within 0.8 m of the target) is what stops the "robot stops dead" look. Combine with `decel` so they ease in.

### B3. Separation and crowding

Sailors shouldn't walk through each other. A cheap local steering pass handles it:

```python
def separation(m, others, dt):
    push = Vec2(0, 0)
    for o in others:
        if o is m: continue
        d = m.pos - o.pos
        r = m.radius + o.radius
        if 0 < d.length() < r:
            push += d.normalized() * (r - d.length()) * 2.0
    m.vel += push  # soft, not a hard resolve
```

Soft separation reads as "people shifting around each other" rather than "physics bodies". For **bottlenecks** (hatch ladders, narrow side decks), add a lightweight **station reservation**:

- Each bottleneck has a capacity (usually 1).
- A sailor entering requests a slot; on release, the next queued sailor gets it.
- Queued sailors switch to an `idle_wait` animation at a few cm apart, facing the bottleneck. This *alone* makes a busy deck look choreographed instead of chaotic.

### B4. Bracing against the sea — the realism multiplier

This is the highest-value trick in the whole doc. A person on a rolling deck does one of three things:

| Condition | Behavior |
|---|---|
| `|roll| < 6°` and task allows | walks normally |
| `|roll| ≥ 6°` and moving | **brace-walk**: reduced speed, wider stance, lean into the roll |
| `|roll| ≥ 10°` or `flooding > 0.4` | **grab rail**: stop, path to nearest rail point, `brace = 1.0`, hold until roll drops |

Implementation:

```python
def update_brace(m, ctx, dt):
    roll = ctx.get("roll", 0.0)
    if abs(roll) > 10.0 or ctx.get("flooding", 0) > 0.4:
        m.brace = approach(m.brace, 1.0, 3.0 * dt)
        m.target = nearest_rail_point(m.pos, ctx["rails"])
    elif abs(roll) > 6.0:
        m.brace = approach(m.brace, 0.5, 3.0 * dt)
    else:
        m.brace = approach(m.brace, 0.0, 2.0 * dt)
```

And in the renderer, `brace` drives the lean angle: `sprite_rotation = -roll_deg * m.brace * 0.7`. A sailor leaning *against* the roll while the deck leans reads instantly as "standing on a boat".

### B5. Animation state machine

No skeletal IK, no foot planting. Six states, blended on `speed` and `brace`:

| State | Trigger | Visual |
|---|---|---|
| `idle_sway` | `speed < 0.05`, `brace < 0.3` | subtle 2-frame sway synced to ship roll phase |
| `walk` | `speed ≥ 0.05` | 4-frame walk cycle, cycle rate ∝ speed |
| `brace_walk` | `speed ≥ 0.05`, `brace ≥ 0.3` | wider stance, slower cycle, lean |
| `brace_hold` | `brace ≥ 0.7` | static, one arm up (grab pose) |
| `work_crouch` | task in `{bail, stow, clear_gear}` | crouched loop, task-specific arms |
| `stand_watch` | task in `{helm, lookout, radio}` | standing, head turns occasionally |

Transition rules: blend over ~0.2 s. Never hard-cut between `walk` and `brace_hold` — that's the tell of a cheap sim.

**Turn toward speakers.** During a conversation, set `facing` toward the current speaker (and stop `m.vel`). This one line makes conversations legible from across the deck.

### B6. Staggering — cheap, effective

When `|roll_rate|` is high and `brace < 0.5`, apply a small lateral impulse to `m.vel` opposing the roll *rate*, magnitude scaled by `(1 - brace)`. Cap it. You'll get sailors who occasionally take a half-step to catch themselves — which is exactly what happens on a real deck. Do **not** let this push them off the ship; clamp to deck bounds.

### B7. Pathing integration

Keep the existing clearance-aware A*. The motion layer consumes the path as a **polyline** and does:

1. Seek the next waypoint with arrival.
2. On arrival within `WAYPOINT_RADIUS` (0.4 m), advance.
3. Re-path on obstruction (another sailor blocking > 1.5 s, or deck state change like a hatch closing).
4. Repath throttle: at most once per 0.5 s per sailor to protect the benchmark budget.

Path smoothing: run a short **funnel / string-pull** pass on the A* output so sailors walk in straight lines around corners instead of hugging the grid.

### B8. The "gather" behavior (conversation prerequisite)

For conversations to happen, sailors sometimes need to *choose* to be near each other. Add a `gather` sub-behavior:

- Select two idle sailors.
- Pick a **meeting spot**: the nearest rail point, a hatch coaming, or a task station between them.
- Both path to it with normal arrival.
- On arrival within `CONVERSATION_RADIUS`, hand off to the conversation system (Part A) and set facing toward each other.

This is the bridge between A and B — and it's why the two systems belong in one doc.

### B9. Performance budget

Sailors are few (≤ 12), so this is cheap. But keep it bounded:

- **O(n²) separation** is fine at n=12 (< 150 pair checks/tick). Revisit past n=30 with a spatial grid.
- **Repath throttle** per sailor (B7.4) is the big one — without it, a crowd re-pathing every frame will blow the tick budget.
- Target: **< 0.15 ms per tick** for 12 sailors on a mid deck, measured in `tools/bench_sailor_motion.py`.

### B10. Minimal module sketch

```python
# fishing_sim/systems/sailor_motion.py
class SailorMotion:
    def __init__(self, pathfinder, rails):
        self.pathfinder = pathfinder
        self.rails = rails
        self.states: dict[str, MotionState] = {}

    def tick(self, dt, sailors, ctx):
        for s in sailors:
            m = self.states.setdefault(s.id, MotionState(pos=s.pos))
            self._update_task_target(s, m, ctx)
            self._update_brace(m, ctx, dt)
            self._follow_path(m, dt, ctx)
            step(m, m.target, dt, ctx)
            separation(m, [self.states[o.id] for o in sailors if o.id != s.id], dt)
            m.pos = clamp_to_deck(m.pos, ctx["deck_bounds"])
            s.pos = m.pos
            s.facing = m.facing
            s.anim = pick_anim(m, s.task, ctx)
```

## Known limitations

- **No IK.** Feet will not plant perfectly on a rolling deck. `brace` + sway + ship transform hides this 95% of the time; a picky eye will still catch it.
- **2D top-down pathing only.** Ladders/stairs are abstracted as bottleneck nodes, not simulated as vertical traversal. Fine for a 2D game; a future 2.5D pass would need per-level decks.
- **Conversation scripts are hand-authored.** No procedural generation of beats. That's a deliberate choice — generated dialogue reads as generated. `BeatGroup` gives variety without that cost.
- **Setpieces are rare by design** and easy to miss if the player is heads-down on a task. If playtesting shows players never see them, the fix is a subtle crew-log entry, not raising the weight.
- **No SFX in this slice** — `ChatterEvent` already carries `category`, so the audio layer can be added later without touching this code.
- **Motion budget assumes ≤ 12 sailors.** Past that, swap separation to a spatial grid and cap the pair-check count.

## Rollout order (recommended)

1. **B1 (ship-local coords) + B2 (arrive/accelerate)** — biggest perceptible win, smallest change.
2. **B4 (brace) + B5 (anim states)** — the realism multiplier.
3. **B3 (separation + bottlenecks)** — makes a busy deck look choreographed.
4. **A1–A3 (tiered scripts, runtime)** — long conversations need calm context and co-located sailors, so this comes after motion.
5. **B8 (gather)** — bridges the two.
6. **A5 setpieces last** — they depend on the MAYDAY/trust data already being stable, which v13.2.05 mostly is.
# Part C — Slip, Trip, and Chain Reaction

**No SFX** — reactions are `ChatterEvent`s only.

## C1. What "rolls with the ship" actually means here

The requirement has three distinct meanings and all three are implemented:

1. **Caused by the roll.** Hazard scales with `|roll_rate|` (deg/s) and sustained list, not just with `roll`. A ship that's been at 15° for a minute is fine; a ship *snapping* through 15° in two seconds is not.
2. **Directed by the roll.** When a sailor loses footing, they slide in the ship-local **downhill** direction derived from current roll and pitch. They slide toward the low rail, the way a real person does.
3. **Rendered on a tilted deck.** Because sailors live in ship-local coords (Part B1), the slide plays out *on the deck as it appears tilted in world space*. They slide downhill across a visibly sloping surface. No extra rendering work — the ship transform carries them.

A slip is not a random animation. It's a **consequence of state** — deck condition × sailor footing × ship attitude — and it reads as one.

## C2. Deck condition model

Each deck region has a **slipperiness** value in `[0, 1]`, driven by what's actually on it.

```python
@dataclass
class DeckRegion:
    name: str                     # "fish_room", "engine", "foredeck", "port_side", ...
    polygon: list[Vec2]           # ship-local
    water: float = 0.0            # 0..1, from flooding / overtopping / rain
    organic: float = 0.0          # 0..1, fish blood, guts, slime
    oil: float = 0.0              # 0..1, fuel / lube spills
    ice: float = 0.0              # 0..1, frost / cold weather
    clutter: float = 0.0          # 0..1, loose gear, lines, buckets

    def slipperiness(self) -> float:
        return min(1.0, 0.55 * self.water + 0.35 * self.organic
                       + 0.45 * self.oil + 0.70 * self.ice)

    def trippiness(self) -> float:
        return min(1.0, 0.50 * self.clutter + 0.20 * self.water)
```

Sources update these values:

| Source | Region | Effect |
|---|---|---|
| Flooding / wave overtopping | affected compartments | `water +=` |
| Catch processing | fish room, cleaning station | `organic +=` |
| Gear fouling cleared | deck where fouling was cut | `organic +=` small |
| Engine maintenance | engine room | `oil +=` |
| Cold night, no heat | exposed decks | `ice +=` |
| Player neglects deck wash | everywhere | `organic` and `clutter` accumulate |

**Wash-down task** becomes the counterplay. Assigning a sailor to `wash_deck` reduces `organic` and `water` in their region. This is the kind of small interaction that makes the sim feel like a system rather than a mood.

Region lookup is a simple point-in-polygon or, if kept to a coarse 1×1 m grid, a bilinear lookup. Both are cheap; use the grid — it avoids fuzzy region boundaries at the edges.

## C3. Footing — the per-sailor state

Every sailor carries a footing scalar recomputed each tick.

```python
@dataclass
class FootingState:
    value: float = 1.0
    last_roll_rate: float = 0.0
    mode: str = "walking"        # walking | slipping | tripped | falling | prone | getting_up | catching
    mode_until: float = 0.0
    slide_vel: Vec2 = Vec2(0, 0)
    knock_vel: Vec2 = Vec2(0, 0)  # from jostles
    injured: str | None = None
    injured_until: float = 0.0
    prone_ticks: int = 0


def compute_footing(m, s, ctx, deck):
    f = 1.0
    f -= 0.45 * deck.slipperiness_at(m.pos)
    f -= 0.30 * ctx.fatigue(m.id)
    f += 0.20 * m.brace
    f -= 0.10 * TASK_PENALTY.get(m.task, 0.0)   # bent over, running, carrying load
    return max(0.0, min(1.0, f))
```

`TASK_PENALTY` values: `bail: 0.15`, `stow: 0.10` (bent over), `clear_gear: 0.12`, `lookout: 0.0`, `helm: 0.05` (one hand on wheel), `wash_deck: 0.20` (hosing your own footing away — dangerous, as it should be).

## C4. Hazard model — continuous, not event-rolled

No dice-rolling every frame. A continuous hazard rate in units of **events per second**:

```python
def slip_hazard(m, s, ctx, deck):
    f = s.value
    foot_f = max(0.0, 1.0 - f) ** 2                # 0 at f=1, 1 at f=0
    roll_f = min(1.0, abs(s.last_roll_rate) / 25.0)
    slip_f = deck.slipperiness_at(m.pos)
    return 0.0004 + 0.030 * foot_f + 0.020 * roll_f * slip_f

def trip_hazard(m, s, ctx, deck):
    if m.speed < 0.3:                               # can't trip standing still
        return 0.0
    foot_f = max(0.0, 1.0 - s.value) ** 2
    trip_f = deck.trippiness_at(m.pos)
    speed_f = min(1.0, m.speed / m.max_speed)
    return 0.0002 + 0.025 * trip_f * speed_f * (0.3 + 0.7 * foot_f)
```

Then in the tick:

```python
p = (slip_hazard(...) + trip_hazard(...)) * dt
if rng.random() < p:
    trigger(mode="slip" if slip_roll > trip_roll else "trip", ...)
```

The `0.0004/s` baseline means ~once per ~40 minutes on a perfectly clean deck. The roll+slip term dominates in weather. **Tune to taste**; see the tuning table in C13.

## C5. Slip vs. trip — distinct behaviors

| | Slip | Trip |
|---|---|---|
| **Trigger** | wet/organic/ice deck × roll rate | clutter × speed × roll |
| **Direction** | toward local downhill (roll+pitch) | forward along velocity |
| **Motion** | slide with friction decay | forward pitch, arrest, then down |
| **Recovery** | catch rail / stanchion / another sailor | stumble-step, sometimes fall |
| **Chain trigger** | sliding body is a moving hazard | tripped body is a static hazard |

Both can produce a **fall**; outcome is rolled:

```python
def roll_outcome(s, deck):
    hard = 0.10 + 0.25 * (1 - s.value) + 0.15 * deck.slipperiness_at(...)
    fall = 0.30 + 0.25 * (1 - s.value)
    if rng.random() < hard:  return "hard_fall"
    if rng.random() < fall:  return "fall"
    return "stumble"
```

- **stumble** (~60%): 0.4 s speed penalty, no task interruption.
- **fall** (~30%): prone 1.2–2.0 s, task interrupted, `fatigue += 0.05`.
- **hard_fall** (~10%): prone 3–4 s, minor injury (`sore_arm` / `bruised_ribs`) for 3–5 min, `fatigue += 0.12`, movement speed −15% until it clears.

No deaths, no long-term damage from a fall. This is a fishing sim, not a roguelike. Falls are **flavor and consequence**, not punishment.

## C6. Sliding with the ship — the physics

The slide moves in ship-local coordinates along the **downhill vector** derived from roll and pitch:

```python
def local_downhill(roll_deg, pitch_deg):
    # +x = forward, +y = starboard (matches Part B ship-local frame)
    # roll > 0 => starboard goes down; pitch > 0 => bow goes down
    gx = math.sin(math.radians(pitch_deg))
    gy = math.sin(math.radians(roll_deg))
    v = Vec2(gx, gy)
    return v.normalized() if v.length() > 1e-4 else Vec2(0, 0)


SLIDE_G = 2.5         # m/s^2, effective push toward the low rail
FRICTION = 3.0        # m/s^2 of decay, reduced by slippery deck

def slide_step(m, s, dt, deck):
    down = local_downhill(m.roll, m.pitch)
    s.slide_vel += down * SLIDE_G * dt
    fric = FRICTION * (1.0 - 0.5 * deck.slipperiness_at(m.pos))
    s.slide_vel -= s.slide_vel.normalized() * fric * dt if s.slide_vel.length() > 0 else Vec2(0, 0)
    m.pos += s.slide_vel * dt
    m.pos = clamp_to_deck(m.pos, deck.bounds)
```

**Catch chance while sliding** — a sailor with good footing grabs a rail, stanchion, or another person and stops:

```python
def try_catch(m, s, ctx):
    if not m.near_rail and not m.near_stanchion and not m.near_sailor:
        return False
    p = 0.30 + 0.40 * m.brace + 0.30 * (1.0 - ctx.fatigue(m.id))
    if rng.random() < p:
        s.slide_vel *= 0.1
        s.mode = "catching"
        s.mode_until = clock + 0.5
        return True
    return False
```

A sailor who can't catch a rail at the edge **presses against it** — clamped by `clamp_to_deck`. Falling overboard is **explicitly out of scope** for this slice; when the MOB rescue system lands, this is where the hook goes. Note it, don't build it.

## C7. Tripping another sailor — the chain

When sailor A is in `slipping`, `tripped`, or `falling` mode and has nonzero velocity, **A is a moving hazard**. Each tick, check for collisions with nearby sailors:

```python
def propagate_collision(A, B, ctx):
    if A.id == B.id: return
    if A.s.mode not in ("slipping", "tripped", "falling"): return
    if B.s.mode in ("prone", "getting_up", "slipping", "tripped", "falling"): return
    if B.chain_depth >= 2: return                          # cap chains at A → B → C

    dist = (A.pos - B.pos).length()
    if dist > A.radius + B.radius + 0.15: return

    impulse = A.s.slide_vel.length() if A.s.mode == "slipping" else 2.0
    if impulse < 0.5: return

    # B gets a footing check against the impulse
    resistance = B.s.value + 0.3 * B.brace + 0.2 * (1 - ctx.fatigue(B.id))
    if rng.random() < resistance * 0.6:
        # stayed up — staggered only
        B.knock_vel += (B.pos - A.pos).normalized() * impulse * 0.4
        B.stumble(0.3)
        return

    # went down
    trigger_trip(B, cause=A.id, direction=(B.pos - A.pos).normalized(),
                 force=impulse)
    B.chain_depth = A.chain_depth + 1
```

Notes:

- **Chain depth capped at 2** (A → B → C, but C can't trip D). Uncapped chains look like slapstick.
- **Prone sailors are static hazards.** A sailor in `prone` mode for 1–2 s blocks their radius like an obstacle. A running sailor who clips them trips.
- **The trip direction is *away* from the falling sailor** — B gets knocked in the direction A is falling toward them, then pitches forward.
- **Trips also happen without an initial slip** — a solo sailor catching their boot on a cleat while running on a cluttered deck.

**Injury propagation is not chained.** Only the primary faller rolls for a hard fall. The tripped party only rolls for stumble-or-fall, never injury. Keeps cascades from being punitive.

## C8. Recovery

```python
def tick_recovery(m, s, dt, ctx):
    if clock >= s.mode_until:
        if s.mode == "prone":
            s.mode = "getting_up"
            s.mode_until = clock + 0.6
        elif s.mode in ("getting_up", "catching", "stumble"):
            s.mode = "walking"
            s.mode_until = 0.0
            s.slide_vel = Vec2(0, 0)
```

`getting_up` still has `brace = 0` and reduced footing — a sailor climbing off the deck during heavy roll is at *elevated* risk of going down again. This is deliberate; it makes the recovery feel real and gives weather weight.

## C10. Conversation hooks

Slips and trips are **conversation fuel**. Emit immediate one-shot `ChatterEvent`s (not full scripts):

```python
SLIP_SELF = ["Whoa—", "Deck's like ice—", "Son of a—", "My feet—"]
SLIP_OTHER = ["You alright?", "Watch your step!", "Get a hand on the rail!",
              "There he goes.", "Mind yourself!"]
TRIP_OTHER = ["Sorry — sorry — didn't see you.", "My fault, my fault.",
              "You came out of nowhere.", "Both of us, then."]
HARD_FALL = ["I'm fine. I'm fine. Give me a second.",
             "Nothing broken. Probably.", "That's going to be stiff tomorrow."]
```

Rules:

- **Self-slip** fires from the faller if `fatigue < 0.8` (an exhausted sailor doesn't quip).
- **Partner reaction** fires from any sailor within 3 m who has line-of-sight. One reaction per fall, 0.5–1.2 s delay.
- **Conversation interruption:** if a conversation is active and a participant slips, that conversation pauses (per Part A3), and a `cut_short` reaction beat fires.
- **Do not auto-start a full conversation** off a slip. It would over-dramatize routine falls. Reactions are one-shots.

## C14. Benchmarks

Target: **< 0.03 ms per tick** for 12 sailors.

Cost breakdown per sailor per tick:

- Footing recompute: O(1)
- Slip/trip hazard: O(1) + 1–2 deck grid lookups (bilinear)
- Collision propagation: O(n) neighbor check, n = 12 → 12 checks
- Recovery: O(1)

Total: ~150 comparisons + 24 grid lookups per tick. Trivially within budget.

The only thing that can blow the budget is **point-in-polygon region lookup** if you skip the grid. Use the grid.

`tools/bench_sailor_footing.py` should time it under the same harness as the existing motion benchmark.

## C15. Known limitations

- **Overboard is not implemented.** A sailor who slides into the rail is clamped against it. Falling over the side needs the MOB rescue system (not in this slice) and is intentionally deferred.
- **Injuries are flavor + small debuffs.** No medkit, no crew hospital, no death. This is a deliberate choice — the point is atmosphere, not punishment. Hooking it to a future medical system is one `@dataclass` field away.
- **Chain cascade is capped at 2.** Uncapped looks like slapstick. If playtesting shows it feels too gamey, raise to 3; if it feels random, drop to 1 (no chains at all).
- **Deck grid is coarse.** 1×1 m means a sailor can slip "on" a puddle they're not quite in. Acceptable at this scale; a finer grid is a one-line change.
- **No audio.** The user asked for no SFX. When it lands, the `ChatterEvent.category` for `slip`, `trip`, `hard_fall` is already the audio hook.
- **Not connected to the sea-over-the-rail system yet.** When `sea_interaction.py` adds water to a compartment, `DeckRegion.water` should be incremented by the same call. Currently the two systems are independent; hooking them is one line in the sea interaction handler and a test.
- **The wash-down counterplay is stubbed.** The region state is there, the task is there, the physics reaction is there — but the `wash_deck` task doesn't yet reduce `organic`/`water` values. That's a one-function addition in `tasks.py` when the task list is next touched.

## D1. Two event types, one output

Sound and text are related but not identical. A scream that a sailor *heard* and a bubble that a viewer *saw* are different things.

```python
@dataclass
class VocalEvent:
    """A physical sound in the ship-local world. Consumed by the hearing system."""
    kind: str                 # "help" | "man_overboard" | "warning" | "grunt"
    speaker: str
    pos: Vec2                 # ship-local
    intensity: float          # 0..1, scream volume
    time: float               # seconds
    source_id: str | None = None  # e.g. overboard sailor, distressed vessel

@dataclass
class ChatterEvent:
    """A visible/delivered bubble. Unchanged from Part A."""
    speaker: str
    text: str
    delay: float = 0.0
    category: str = ""
    tier: int = 0             # 0 near, 1 distant — UI renders smaller
```

A `VocalEvent` is always emitted. A `ChatterEvent` is only emitted to sailors whose **hearing roll** passed (and to the UI bubble layer if the player camera is close enough). Distant sailors get an *internal* reaction without a visible bubble — that's the "silent confusion" state.

## D2. Hearing model

Per listener, per vocal:

```python
@dataclass
class HearingProfile:
    base_range: float = 22.0        # meters, calm conditions
    attention: float = 1.0          # 0..1, modulated by task focus
    occlusion: float = 1.0          # 0..1, walls/engine room
    fatigue_penalty: float = 0.3    # how much fatigue muffles

def hearing_probability(vocal: VocalEvent, listener_id: str, ctx) -> float:
    ambient = (0.55 * min(1.0, ctx.sea_state / 6.0)
               + 0.30 * ctx.wind_norm
               + 0.15 * ctx.rain_norm)               # 0..1
    rng_m = 22.0 * vocal.intensity * (1.0 - 0.70 * ambient)
    h = listener_hearing(listener_id)                # profile
    rng_m *= h.occlusion
    dist = (ctx.pos(listener_id) - vocal.pos).length()
    if dist >= rng_m:
        return 0.0
    p = (1.0 - dist / rng_m) * h.attention
    p *= (1.0 - h.fatigue_penalty * ctx.fatigue(listener_id))
    p *= (1.0 - 0.40 * ambient)
    return max(0.0, min(1.0, p))
```

**Calm deck, `intensity=0.9`: ~20 m. Force 6 + rain: ~5 m.** An engine room adds `occlusion = 0.3`; a radio operator on headphones `occlusion = 0.6`; an exhausted sailor at 0.9 fatigue has `attention ≈ 0.5`.

Only **one roll per vocal per listener** — not per frame. Fire the roll once at the moment of emission, log it, done.

**Deafness, headphones, engine room** are all just `occlusion` and `attention` knobs. No special cases.

## D3. The help scream

### D3.1 Sliding toward the rail

Trigger: `mode == "slipping"` AND `slide_vel.length() > 1.2` AND heading within 45° of a rail — i.e. they're going to hit something.

```python
def maybe_help_scream_slip(m, s, ctx):
    if s.help_screamed_at and clock - s.help_screamed_at < 1.5:
        return
    if s.slide_vel.length() < 1.2:
        return
    if not heading_toward_rail(m, threshold_deg=45):
        return
    intensity = 0.4 + 0.5 * min(1.0, s.slide_vel.length() / 4.0)
    intensity *= (1.0 - 0.3 * ctx.fatigue(m.id))   # exhausted people scream weaker
    emit_vocal(VocalEvent("help", m.id, m.pos, intensity, clock))
    emit_chatter(m.id, pick(HELP_LINES), category="help")
    s.help_screamed_at = clock
```

`HELP_LINES = ["Help—!", "Whoa— grab me!", "I'm going—", "Rail! Rail!"]`

### D3.2 After falling over

Every ~2.5 s the overboard sailor emits a `help` vocal with **intensity decaying over time** — panic fades, then revives on a wave:

```python
def overboard_voice_tick(m, s, dt, ctx):
    if clock < s.next_scream:
        return
    panic = max(0.35, 1.0 - 0.05 * (clock - s.overboard_since))
    intensity = panic * (0.7 + 0.3 * math.sin(clock * 0.7 + s.seed))
    emit_vocal(VocalEvent("help", m.id, m.pos, intensity, clock))
    emit_chatter(m.id, pick(OVERBOARD_LINES), category="overboard")
    s.next_scream = clock + 2.2 + rng.uniform(-0.4, 0.6)
```

`OVERBOARD_LINES = ["Help! I'm in the water!", "Over here! Over here!",
"Can't get a grip—", "Under— under— *cough* —here!"]`

**Storm drowns the scream.** That's just `hearing_probability` doing its job with high `ambient`. A sailor at 0.4 fatigue screaming in a Force 6 storm is heard by only the sailor five meters away — and maybe not even them. This is the feature, not a bug.

### D3.3 Not screaming in some states

No help scream if:
- `mode == "prone"` and `injured == "winded"` — can't get breath yet
- `mode == "getting_up"` — recovering, quiet
- The sailor is `in_conversation` and the scream would be interpreted as an interruption (they pause instead)

## D4. Catch attempt

While A is sliding/falling, every sailor B within **1.1 m** of A's path gets a **reaction window**.

```python
@dataclass
class CatchAttempt:
    rescuer: str
    victim: str
    started: float
    duration: float = 0.4
    result: str | None = None   # "success" | "miss" | "chain" | "unavailable"
```

### D4.1 Eligibility

B is eligible if **all**:

- `B.mode == "walking"` (not already prone/sliding)
- `B.task not in ("helm", "radio")` — a helmsman can't let go of the wheel; a radio operator hears it and relays (see D6)
- `B.footing > 0.25` — too unsteady to catch anything
- `B.brace < 0.9` — not clamped to a rail themselves
- `B.attention` — not deeply focused (e.g. deep in a stow task during a storm)

If ineligible, B emits a **guilt chatter** (`"I can't reach—"`) but doesn't attempt. This matters for the relationship system.

### D4.2 Success roll

```python
def catch_success_probability(A, B, ctx, rel):
    p = 0.35
    p += 0.25 * B.footing
    p += 0.15 * B.brace
    p -= 0.20 * ctx.fatigue(B.id)
    p += 0.20 * rel.trust_clamp()          # they know how they move together
    p += 0.10 * rel.familiarity            # used to working with this person
    p -= 0.25 * min(1.0, A.slide_vel.length() / 4.0)   # harder to stop a fast body
    return max(0.05, min(0.95, p))
```

A familiar, trusting pair almost always saves each other. Strangers miss more often. This is the first place where **relationship state has a mechanical consequence**, not just flavor — it's why the relationship matrix exists.

### D4.3 Outcomes

**Success** (`0.65` default, modulated above):

- A's `slide_vel *= 0.1`, `mode = "catching"`, `mode_until = now + 0.6`
- B's `mode = "catching"`, `mode_until = now + 0.6`, `brace = 0.8`
- Both get `ChatterEvent` bubbles: A `"Thanks— thanks—"`, B `"Got you."`
- `rel(A→B).trust += 0.25`, `rel(A→B).familiarity += 0.15`, `rel(B→A).trust += 0.10`
- `B.debts_saved += 1`, `A.debts_owed += 1`
- `s.help_screamed_at` reset (they got helped)

**Miss** (`~0.30`):

- B's `brace` becomes `0.3`, `footing -= 0.2` — they lurched
- B emits `"No— no— grab the rail!"`
- A continues sliding
- `rel(A→B).grievance += 0.08` (irrational — but a near miss does that)
- B emits a later guilt line at the next calm moment (`"I couldn't hold him."`) if A went over

**Chain** (`~0.05`, only if `A.slide_vel > 3.0`):

- B's velocity is bumped by A's impulse (per C7)
- B is pulled into `slipping` mode too
- If B has a rail nearby, B catches it; otherwise B is at risk of overboard themselves
- Both A and B now slide together — visually a real disaster
- `rel(A→B).trust += 0.05` (they tried), `rel(B→A).trust += 0.0` (neutral — B didn't cause it)

The **chain case** is what makes Part C's "tripping another sailor" feel narratively complete rather than mechanically isolated.

### D4.4 At the rail

If A reaches the rail:
- **Rail catch** (per C6) — A stops at the rail, safe.
- If A's `slide_vel > 3.0` at contact → overboard (see D5).
- If A's `slide_vel > 1.5` and B is within reach and trying to catch → last-chance roll (the D4.2 probability re-rolled with `+0.15`) — the cinematic "hand grabs hand" moment.

This is the one place I'd allow a **deterministic override**: if `rel.familiarity > 0.7` and B is at the rail, force success. It's earned familiarity, and it's a **one-time narrative moment** worth keeping, not a balance concern.

## D6. MAN OVERBOARD — the alarm chain

### D6.1 The chain, step by step

1. **A goes overboard.** A begins emitting `help` vocals (per D3.2), attenuated by weather.
2. **A witness B** is any sailor who **heard** A's first post-overboard help vocal (one roll, D2).
3. **B screams "MAN OVERBOARD!"** — a single, loud vocal:
   ```python
   VocalEvent("man_overboard", B.id, B.pos, intensity=1.0, clock)
   ```
   Only the **first witness** screams. No chorus. If a second witness also heard it, they enter `witness` state but don't scream — they look toward the rail, then toward B.
4. **C hears the MOB scream.** The MOB vocal has a wider base range (`base_range * 1.6`) — a scream directed at the whole ship, not just the nearest hand.
5. **C runs to the wheelhouse.** The **nearest C to a clear path** is chosen. Selection rule:
   ```python
   def choose_runner(heard_mob, ctx):
       candidates = [s for s in heard_mob
                     if s.task not in ("helm", "radio")   # already there or already on radio
                     and s.mode == "walking"]
       return min(candidates, key=lambda s: wheelhouse_path_cost(s), default=None)
   ```
   If no sailor heard the MOB scream, **no runner is dispatched.** The MOB alarm does not propagate. This is the whole point: storms and engine rooms kill alarms.

### D6.2 The runner's journey

`state.mode = "running_to_wheelhouse"`. This is the **only state where normal caution is suspended**:

- `max_speed *= 1.6`
- `brace` ignored for speed, but still applies to footing — **the runner slips more often** (per Part C hazard, `speed_f` goes up)
- If the runner slips and doesn't go overboard, they get up and keep running
- If the runner trips over a prone sailor (C7), they both go down, and the runner **must re-roll to resume** — there's a real chance they don't make it
- The runner screams `"MAN OVERBOARD!"` again every 4 s, propagating the alarm to others who missed the first

This is where the sim's systems interlock: **weather affects hearing → hearing affects alarm → alarm affects whether the wheelhouse knows → the wheelhouse runs the rescue**. Every link can fail.

On reaching the wheelhouse:

- Interact with helm/radio: trigger `ctx.raise_mob_alarm()` — the existing sim's hook
- The runner's task becomes `helm` or `radio` (whichever is free)
- The runner emits `ChatterEvent(category="mob", text="MAN OVERBOARD — port side, stern!")`
- Any sailor who **heard** the wheelhouse alarm but not the original is now a **witness** and can be assigned recovery tasks

```python
    self.mob_sailor = sailor_id

```

## D7. Relationship matrix — the social state

### D7.1 Data model

Per sailor, a sparse dict of relationship records. Bidirectional by default (symmetric), asymmetric modifiers on top.

```python
@dataclass
class Relationship:
    trust: float = 0.0          # -1..1
    familiarity: float = 0.0    # 0..1
    grievance: float = 0.0      # 0..1, minor grievances decay
    debts_saved: int = 0        # times I saved them
    debts_owed: int = 0         # times they saved me

@dataclass
class SocialState:
    rel: dict[str, Relationship] = field(default_factory=dict)

    def get(self, a, b):
        return self.rel.setdefault((a, b), Relationship())
```

`rel` is a defaultdict keyed by `(min(a,b), max(a,b))` tuple so direction is handled by explicit fields on the shared record — but note the "who saved whom" asymmetry lives in `debts_saved` / `debts_owed`, which **is** directional.

### D7.2 Events that update it

| Event | Update |
|---|---|
| B catches A sliding | `A→B trust +0.25`, `B→A trust +0.10`, `A→B familiarity +0.15`, `B.debts_saved += 1` |
| B tries and misses A | `A→B grievance +0.08`, `B→A (none)` |
| B fails to reach A at the rail (A goes over) | `B.guilt += 0.3` (a separate scalar on B, no relationship change) |
| B heard MOB, ran to wheelhouse | `A→B trust +0.30`, `B→A trust +0.15` (on successful recovery) |
| B heard MOB, didn't run (ineligible) | no change |
| B heard MOB, was eligible, but froze | `A→B grievance +0.15` (rare; freeze rolls are separate) |
| B didn't hear MOB | no change — **ignorance is not a sin** |
| A shared a long conversation with B (Part A) | `familiarity += 0.05` per conversation |
| Shared task for 5+ min | `familiarity += 0.01/min` |
| A argued with B during conversation | `grievance += 0.05` (see Part A's argument beat) |

Grievance **decays** at `0.002/s` — grudges fade, slowly. Familiarity never decays. Trust drifts toward 0 very slowly (`0.0005/s`).

### D7.3 Why it matters mechanically

- **Catch probability** (D4.2) reads `rel.trust` and `rel.familiarity`. Familiar pairs save each other more.
- **Conversation tiers** (Part A1) get a `+` weight when `familiarity > 0.6`, `-` when `grievance > 0.4`.
- **Conversation tone** (the `rapport_warm` / `rapport_cold` lines from A5) is retargeted to be **pair-specific** — after a save, the saved sailor's lines toward the rescuer carry a different flavor.
- **Task assignment** (right-click context menu) — assigning a task to a sailor who has positive `rel.trust` toward another sailor completes 10% faster when co-located. Assigning to a pair with high `grievance` is 10% slower. Small, always-on.

This is how the relationship system is **felt**, not just tracked.

### D7.4 Save/load

The relationship matrix **is** persistent. It's the one part of this doc that must go into the M10 save system. Format:

```python
{
  "relationships": [
    {"a": "s1", "b": "s2", "trust": 0.4, "familiarity": 0.6,
     "grievance": 0.0, "saved_a_by_b": 1, "saved_b_by_a": 0}
  ]
}
```

Trivial to serialize; add it to the M10 checklist explicitly.

## D8. Chatter and UI integration

### D8.1 Bubbles for what the player sees

A player camera near a vocal source sees the bubble (`ChatterEvent`). Distant players see nothing — they only notice the *effect* (a sailor running to the wheelhouse, an empty spot on deck). This is the gameplay: **the player must also hear the screams.**

The player camera's effective hearing profile:

```python
HEARING_PROFILE_PLAYER = HearingProfile(base_range=28.0, attention=1.0, occlusion=1.0)
```

At 28 m in a calm sea, the player hears a scream. At 5 m in a Force 6, they might not. This makes weather dangerous for *the player* in a way that doesn't just reduce stats.

### D8.2 Conversation interruption

Part A3's pause logic already handles CRITICAL context. Add `help`, `man_overboard`, and `overboard` vocals as **CRITICAL** for participants within earshot:

```python
def vocal_interrupts_conversation(vocal, participants, ctx):
    if vocal.kind not in ("help", "man_overboard"):
        return False
    for p in participants:
        if rng.random() < hearing_probability(vocal, p, ctx):
            return True
    return False
```

If interrupted, the conversation pauses with a `cut_short` beat, the speaker turns toward the sound (`facing` toward `vocal.pos`), and the responder runs if the task allows.

### D8.3 Crew log

Every `VocalEvent` that reaches **at least one sailor** is written to the crew log with a `heard_by=[...]` list. The player can inspect the log later and see "A screamed; B heard; C did not" — this is the readable record of what the alarm chain actually did.

This is also how a player learns that storms deafen crews without a tutorial.

## D12. Known limitations

- **No rescue boat, no swimming, no hypothermia.** Overboard sailors tread water and can be recovered via the sim's existing rescue hook. This part only gets them into the water and raises the alarm. Everything past `notify_mob()` is the existing v13.2.05 rescue flow.
- **Single MOB at a time.** If two sailors go overboard within seconds, only the first raises the alarm. A multi-MOB chain is a Phase B follow-up and would require re-thinking the runner selection.
- **Freeze is a stub.** The "heard MOB, was eligible, froze" case is a `grievance` update without a visible animation. A future slice could add a `frozen` state with a 1–2 s animation; for now the update fires immediately.
- **The MOB vocal is not localized.** `"MAN OVERBOARD"` is the only line. If the ship's crew is themed (nationality, era), swap the line bank.
- **No player-driven catch.** A player watching a slide can't grab a sailor directly. If input controls are on the roadmap, hooking `catch_attempt` to a button is one line — but this doc doesn't assume input exists.
- **Relationships are symmetric + asymmetry fields.** If directionality is ever needed for trust itself (not just debts), the record supports it — but the current code updates trust on both sides. Named asymmetry is only in `debts_saved`/`debts_owed`. This is deliberate; too much asymmetry makes the matrix unreadable to playtesters.
- **No injuries from catch attempts.** B's lurch is cosmetic. A hard catch *should* hurt the rescuer sometimes, but adding that to an already multi-systems slice is risk; it can be a `0.15` chance in a later tuning pass.
- **Hearing roll is per-vocal, not per-frame.** A vocal emitted once is heard-or-not heard, permanently. This is correct (real sound is transient) but means a sailor who just woke up can't "hear it again" — reactions are one-shot, and that's fine.
- **Overboard animation is a bobbing head.** The wave surface returns a Y coordinate; the sailor sprite is placed just above it. No swimming pose, no arms-out stroking. Deliberate.
- **Chains of tripping during a run to the wheelhouse are not modeled.** If the runner trips, they get up and continue. If they trip *over a prone sailor*, both go down and the runner re-rolls to resume. A full cascade is out of scope.

# Part E — Work, Rest, and Hypothermia

**Module:** `fishing_sim/systems/sailor_work.py`
**Replaces:** the implicit "sailor stays on task forever" behavior.

## E1. The rest requirement is real

Commercial fishing crews work **six-hour watches with six hours off** (two four-hour watches per 24 h is also documented), and the legal floor is **10 hours of rest per 24 hours** and **77 hours per seven-day period**. Deckhands, however, work *sequentially*: short recovery periods between shots, with rest driven by catch volume — not by the clock alone.

So the model is **two clocks, not one**:

| Clock | Driver | Behaviour |
|---|---|---|
| **Watch clock** | Fixed rotation (6-on / 6-off or 4-on / 8-off) | Sailors are assigned to a watch; only the on-watch crew are eligible for deck tasks |
| **Fatigue clock** | Accumulated work minus accumulated rest | Drives slip hazard (Part C), hypothermia risk, and catch probability (Part D) |

## E2. Data model

```python
@dataclass
class WorkState:
    watch: str = "A"                 # A / B / C
    on_watch: bool = True
    duty_since: float = 0.0          # clock
    rest_since: float = 0.0
    accumulated_rest_24h: float = 0.0
    accumulated_rest_7d: float = 0.0
    fatigue: float = 0.0             # 0..1, feeds Part C and D
    hypothermia: float = 0.0         # 0..1, see E4
    seeking_rest: bool = False       # set by fatigue/hypothermia; overrides task assignment
```

## E3. The rest transition (the "go down the quarters" moment)

A sailor does **not** auto-teleport to their bunk. The transition is a **behaviour**, not a state flag:

```python
def should_seek_rest(s: WorkState, ctx) -> bool:
    if s.fatigue > 0.85:
        return True
    if s.hypothermia > 0.55:
        return True
    if s.accumulated_rest_24h < 6.0 and ctx.hour >= 22:
        return True
    return False
```

When `should_seek_rest` is true:

1. **Task is released** to the pool (the sailor does not just stop — the task becomes available for reassignment; see E6).
2. **Sailor paths to quarters** using the existing Part B motion layer. They walk; they don't vanish.
3. On arrival, `mode = "resting"`, `fatigue` decays at `0.003/s` (≈ 5.5 min from 0.85 to 0.0), `hypothermia` decays at `0.0015/s` plus the warmth bonus of the quarters (E4).
4. **They return to work** when `fatigue < 0.35` and `hypothermia < 0.2`, and a task is available. **They do not auto-return to the exact task they left** — they re-enter the task pool. This is the "go back out again" loop, and it means the ship genuinely changes shape as the watch progresses.

**Co-located rest**: quarters have a capacity (2–4 bunks). If full, a sailor in `seeking_rest` waits in the crew mess, or — if hypothermic — sits by the engine room and accepts a slower recovery. This produces the very real problem of *a cold crew with no warm space left*.

## E4. Hypothermia

Hypothermia is a **separate scalar from fatigue**, driven by exposure, not by effort.

```python
def hypothermia_rate(s, ctx, deck) -> float:
    air = ctx.air_temp_c                 # 0..30
    wind = ctx.wind_norm                 # 0..1
    wet = deck.water_at(ctx.pos(s.id))   # 0..1
    spray = ctx.spray_norm               # 0..1, from sea state + heading

    exposure = (0.40 * max(0.0, (12 - air) / 12)     # cold air
              + 0.30 * wind
              + 0.20 * spray
              + 0.10 * wet)

    warmth = 0.0
    if s.task == "rest" and in_quarters(s):       warmth += 0.60
    if s.task == "helm" and in_wheelhouse(s):      warmth += 0.35
    if near_engine_room(s):                        warmth += 0.25
    if s.task == "bail":                           warmth += 0.20   # hard work generates heat
    if s.task == "radio":                          warmth += 0.15

    return 0.00035 * exposure * (1.0 - 0.7 * warmth)
```

| Value | State | Behaviour |
|---|---|---|
| 0.0–0.25 | Cold but functional | No mechanical penalty |
| 0.25–0.55 | Shivering | `footing -0.15` (Part C), `catch_p -0.10` (Part D) |
| 0.55–0.80 | Onset | `seeking_rest = True`, `fatigue` climbs ×1.5, speech slows |
| > 0.80 | Serious | `mode = "incapacitated"`; another sailor must assist them below (Part D's catch/assist vocabulary applies) |

**No death from hypothermia in this slice.** Serious hypothermia hands off to the existing medical/rescue hook, same as overboard in Part D5.

**The counterplay** is warm spaces, warm tasks, and rotating crew off wet decks. A captain who ignores it will have a shivering, slow, slip-prone crew — which compounds with Parts C and D exactly as it should.

## E5. Watch rotation affects what's possible

- A task can only be assigned to an **on-watch** sailor. Off-watch sailors are in quarters or resting.
- If a task is urgent (flooding, MOB), **any** sailor can be roused — but they start at elevated `fatigue` and a `-0.20` footing penalty for 60 s. Emergency labour is expensive.
- The watch table is data, not code:

```python
WATCHES = {
    "A": [(6, 12), (18, 24)],
    "B": [(12, 18), (0, 6)],
}
```

This is a one-line change to support 4-on/8-off or 6-on/6-off.

## E6. Task handoff (the "better work system")

Replacing "sailor is assigned and stays assigned":

```python
@dataclass
class TaskSlot:
    name: str                 # "helm", "bail", "stow", "clear_gear", ...
    station: Vec2             # ship-local
    assigned_to: str | None
    handoff_pending: bool = False
    priority: int = NORMAL
```

Tick logic:

1. If the assigned sailor becomes `seeking_rest` or `incapacitated`, set `handoff_pending = True`.
2. The task dispatcher assigns the **nearest eligible on-watch sailor** whose current task priority is lower.
3. The departing sailor emits a handoff chatter line (`"Take the wheel — I'm done in."`) and paths to quarters.
4. The incoming sailor paths to the station. Until they arrive, `assigned_to = "in_transit"` and the task is **effectively unmanned** — this is the gap that makes a tired crew dangerous.

This is the system that makes watch rotation *mean* something: tasks actually go untended during handoffs.

# Part F — Bird Sightings and Autofishing Spots

**Module:** `fishing_sim/systems/birdwatch.py`, additions to `autofishing.py`

## F1. What the birds actually mean

Flock of birds is a **very good indication of the possibility of tuna**, because birds feed on baitfish driven to the surface by large pelagic predators; the association runs both ways — birds profit from tuna feeding, and tuna profit from bird diving noise. Fishermen have used seabirds as indicators of fish shoals and underwater banks for as long as there has been commercial fishing.

**This is not a random spawn.** It is a **report → investigate → mark** loop.

## F2. Sighting

Each tick, a lookout (or any sailor with line-of-sight to the sea surface) runs a spawn check:

```python
def bird_sighting_check(ctx, sailor, dt) -> BirdSighting | None:
    # rich water + daylight + visibility
    p = ctx.fish_density_near(sailor.pos)
    p *= 0.6 if ctx.night else 1.0
    p *= 0.4 if ctx.fog else 1.0
    p *= sailor.attention           # a focused deckhand misses it
    if rng.random() > p * 0.0004 * dt:
        return None
    return BirdSighting(
        pos=ctx.random_surface_point_near(sailor.pos, radius=800),
        species=pick(["gull", "tern", "shearwater", "gannet", "albatross"]),
        intensity=rng.uniform(0.3, 1.0),   # flock size / agitation
        behaviour=pick(["circling", "diving", "rafting"]),
    )
```

`behaviour` matters: **diving** birds indicate active surface feeding (highest value); **circling** is moderate; **rafting** (sitting on the water) is low-value — often just resting birds.

## F3. The report

The sailor **reports to the captain**, not to an autofishing system. This is a vocal + task event, not a menu popup.

```python
VocalEvent("bird_sighting", sailor.id, sailor.pos,
           intensity=0.7, time=clock, payload=sighting)
```

- If the captain (or the player at the helm) is within hearing range (Part D2), the sighting enters the **captain's log** and appears on the chart as an **unconfirmed mark**.
- If no one hears it, the sighting **does not enter the log** — the bird flock was real, but the ship missed it. This is the same conditional-hearing logic as the MOB alarm, and it is the point.
- The reporting sailor gets a `+0.05` familiarity bump with the captain if the report leads to a mark.

## F4. Marking as an autofishing spot

A bird sighting becomes a **fishing spot** when:

1. The sighting was **heard** (F3), and
2. The player or an AI officer **investigates** (steams within `CONFIRM_RADIUS` = 400 m), and
3. A confirmation check passes:

```python
def confirm_spot(sighting, ctx) -> FishingSpot | None:
    p = sighting.intensity
    p *= 1.4 if sighting.behaviour == "diving" else 1.0
    if rng.random() < p:
        return FishingSpot(
            pos=sighting.pos,
            quality=sighting.intensity,
            source="bird",
            expires_at=clock + rng.uniform(1800, 7200),
            species_hint=guess_species(sighting.species, ctx),
        )
    return None
```

**Spots expire.** Real feeding aggregations move; a mark from two hours ago is stale. This means autofishing has to *keep finding* new spots, not just visit a fixed list.

## F5. Autofishing integration

`autofishing.py` gains a **spot discovery priority**:

```
priority = spot.quality
         * (1.0 - distance_penalty(spot.pos))
         * freshness(spot.expires_at - clock)
         * (1.0 if spot.source == "bird" else 0.8)   # bird-sourced spots are trusted
```

When no spot is available, autofishing falls back to the existing behaviour (patrol / previous mark). It does **not** invent spots — if the crew didn't see birds, there is nothing to fish.

## F6. Negative indicators

The same literature notes **too many sperm whales or dolphins in one area is a sign to leave** — tuna will be scarce or moving too fast. Add `negative_indicator` sightings:

- Whale/dolphin pod sighted → the current spot's `quality` is reduced, and if it drops below a threshold, autofishing abandons it.
- This is reported the same way (sailor → captain → log) and is just as easy to miss in bad weather.

# Part G — Fuel and Ice Are Decisions, Not Auto-Return

**Module:** `fishing_sim/systems/voyage_decision.py`
**Replaces:** the automatic "return to dock when X" rule.

## G1. The real budget

A tuna longliner typically carries enough fuel for **about four weeks of steaming**, and trips are **one to three weeks** because fish starts spoiling after three weeks. A 20 m longliner might burn **~900 L per 24 h** of operation and carry **25,000 L**, giving **6,000+ nautical miles** of range.

Ice is the tighter constraint. Rough rule: **1 tonne of ice per 2 tonnes of fish** if kept more than a week; **0.7 t ice per 2 t fish** if kept less than a week. Ice boats need **3–5 t of hold space to chill 1 t of fish** (the ice itself takes space).

So the return decision is a **three-way squeeze**, and the game should make the player feel all three:

| Resource | Depletes by | Consequence of running out |
|---|---|---|
| **Fuel** | steaming + running generator | no propulsion, no pumps (Part C/D depend on power) |
| **Ice** | catch volume × storage time | catch spoils, value drops, trust/reputation drops |
| **Hold space** | catch volume | cannot stow more fish; fishing must stop |

## G2. The decision model

Autoreturn is replaced by a **voyage evaluator** that runs when the captain requests it (or periodically for an AI captain), and returns a ranked recommendation — not an order.

```python
@dataclass
class VoyageState:
    fuel_l: float
    fuel_burn_rate_lph: float          # from speed + generator load
    ice_kg: float
    hold_free_m3: float
    catch_kg: float
    hours_since_last_ice: float
    distance_to_port_nm: float
    current_speed_kn: float

@dataclass
class ReturnOption:
    action: str                        # "continue" | "return_now" | "return_soon" | "seek_ice"
    reason: str                        # human-readable, shown to player
    urgency: float                     # 0..1
    survival_margin_h: float           # hours of fuel/ice left beyond the trip home
```

```python
def evaluate_voyage(v: VoyageState) -> list[ReturnOption]:
    hours_home = v.distance_to_port_nm / max(0.1, v.current_speed_kn)
    fuel_home = v.fuel_l / max(1.0, v.fuel_burn_rate_lph)

    fuel_margin = fuel_home - hours_home - RESERVE_H
    ice_margin  = estimate_ice_hours(v) - hours_home - ICE_RESERVE_H
    hold_margin = v.hold_free_m3

    options = []

    if fuel_margin < 0:
        options.append(ReturnOption("return_now",
            "Not enough fuel to make port with reserve", 1.0, fuel_margin))
    elif fuel_margin < 24:
        options.append(ReturnOption("return_soon",
            "Fuel margin under 24 h — weather could close the window", 0.7, fuel_margin))

    if ice_margin < 0:
        options.append(ReturnOption("return_now",
            "Catch will spoil before you make port", 0.95, ice_margin))
    elif ice_margin < 36:
        options.append(ReturnOption("return_soon",
            "Ice short for the steam home at current catch rate", 0.6, ice_margin))

    if hold_margin < HOLD_CRITICAL_M3:
        options.append(ReturnOption("return_now",
            "Hold nearly full — no room to stow the next set", 0.85, hold_margin))

    if not options:
        options.append(ReturnOption("continue",
            "Fuel, ice, and hold all healthy", 0.0, min(fuel_margin, ice_margin)))

    return sorted(options, key=lambda o: -o.urgency)
```

**`seek_ice`** is the interesting middle option: if the ship is near a supply vessel or a port with ice but doesn't need to end the trip, the evaluator can recommend re-icing rather than returning. This is a real longline pattern (supply vessels, re-icing stops) and it gives the player a third choice beyond "fish" and "go home".

## G3. The player sees reasons, not a slider

The UI shows the `reason` string and the `survival_margin_h` as a **negative countdown** when it's shrinking. No "auto-return at 20% fuel" toggle. The captain decides; the system tells them what the numbers actually imply.

**If the captain ignores the recommendation**, the consequences are the existing systems doing their job:

- Fuel out → pumps stop (Part C flooding), helm sluggish, Part D rescue flow if adrift.
- Ice out → `catch_quality` decays per hour past the ice margin, and the next port's buyer price drops.
- Hold full → autofishing stops, and the crew has nothing to do but steam home (or wait, burning fuel).

# Part H — Anchor: A Real Anchor, a Real Chain, a Real Swing

**Module:** `fishing_sim/systems/anchor.py`
**Replaces:** "anchor = position freeze."

## H1. Scope and catenary are the whole model

The holding power of an anchor comes from the **chain lying horizontal on the seabed**; the ratio of chain paid out to water depth (the **scope**) is the key factor, and class guidance is **6:10 minimum** (6 m of chain per 1 m of depth). In sheltered water the environmental envelope is **wind ≤ 25 m/s**, current ≤ 4.8 kn; in open water it tightens to **wind ≤ 11 m/s, significant wave height ≤ 2 m**.

The chain's **catenary** — its sag — absorbs shock; without it, snatching loads can break the anchor out or drag it.

## H2. State

```python
@dataclass
class AnchorState:
    deployed: bool = False
    chain_out_m: float = 0.0
    depth_m: float = 0.0
    scope: float = 0.0                  # chain_out / depth
    holding: bool = True
    dragging: bool = False
    snubber_attached: bool = False      # nylon snubber reduces snatch (optional task)
    anchor_pos_world: Vec2 = None       # where the anchor actually is
    swing_radius_m: float = 0.0
```

## H3. Deploying

1. **Crew task `anchor_party`** assigned (Part E). Requires **2 sailors** — one at the windlass, one at the brake.
2. Ship must be **near zero speed over ground** before letting go; approaching too fast makes the anchor uncontrollable.
3. Chain is paid out to `chain_out = depth * scope_target`. `scope_target` defaults to **6.0** (6:10).
4. `swing_radius_m = chain_out + ship_length` — this is the circle the ship can wander within, and it is **visible on the chart**.

**If scope < 6:0**: the anchor is **at risk of dragging**. A UI warning fires, and the holding probability drops per H4.

## H4. Holding, dragging, and the ship *moving*

An anchored ship is **not frozen**. Each tick:

```python
def anchor_tick(a: AnchorState, ship, ctx, dt):
    if not a.deployed:
        return
    a.scope = a.chain_out_m / max(1.0, a.depth_m)

    # environmental load
    wind_force = ctx.wind_norm ** 2
    wave_force = (ctx.wave_height_m / 2.0) ** 2
    current_force = (ctx.current_kn / 3.0) ** 2

    load = 0.6 * wind_force + 0.3 * wave_force + 0.1 * current_force

    # holding capacity from scope
    hold = clamp((a.scope - 3.0) / 3.0, 0.0, 1.0)     # scope 6:0 => 1.0
    if a.snubber_attached:
        load *= 0.75                                    # snubber damps snatch

    if load > hold:
        a.dragging = True
        drift_dir = ctx.wind_and_current_vector().normalized()
        ship.pos_world += drift_dir * DRAG_SPEED * dt
    else:
        a.dragging = False
        # ship swings around the anchor, not fixed
        ship.pos_world = swing_around(a.anchor_pos_world, a.swing_radius_m, ctx, dt)
```

**The ship swings.** It arcs around the anchor point with the wind and current, and it **drifts if the anchor drags**. This is the requested behaviour: the anchor is a constraint, not a freeze.

## H5. Weighing anchor

1. Crew task `weigh_anchor`. The windlass lifts the anchor and roughly **three lengths of chain (≈ 82.5 m)** is its designed capacity.
2. Ship must **steam slowly up to the anchor** to break it out; the helm task and anchor party must be co-ordinated.
3. If the ship is moving too fast, the chain **snubs** — a shock load that can part the chain or damage the windlass. Model this as a `snub_event` with a probability scaled by speed and no snubber.
4. On completion, `deployed = False`, `chain_out = 0`.

## H6. Tests

| Test | Assertion |
|---|---|
| `test_anchor_requires_zero_speed` | deploying above threshold → warning, holding reduced |
| `test_scope_below_six_reduces_holding` | scope 4:0 → holding capacity low |
| `test_ship_swings_not_frozen` | deployed anchor, changing wind → ship position changes within swing circle |
| `test_drags_in_storm` | wind=20 m/s, scope=6:0 → `dragging = True` |
| `test_snubber_reduces_drag` | same conditions with snubber → load < hold, no drag |

# Part I — Autodock: Anchor, Moor, Gangplank (No Autoshore)

**Module:** `fishing_sim/systems/docking.py`
**Replaces:** "auto-return to dock = teleport ashore."

## I1. Three distinct phases, not one

Real docking prep requires **fenders placed and lines prepared** before the manoeuvre, and the vessel must not be left unattended even with a dock-holding feature active. Autodock is therefore **three separate operations**, and each can fail independently.

### Phase 1 — Approach and anchor (or pick up a buoy)

The ship approaches the harbour at reduced speed. The **anchor party** is on the foredeck. In tight harbours the ship may anchor off and **veer down** on the chain, or pick up a **harbour buoy** — both are common for fishing vessels and both are modelled as `mooring_mode = "anchor"` or `"buoy"`.

### Phase 2 — Mooring

```python
@dataclass
class MooringState:
    mode: str = "none"                 # none | anchor | buoy | alongside
    lines: dict[str, bool] = field(default_factory=lambda: {
        "bow_spring": False, "stern_spring": False,
        "bow_line": False, "stern_line": False,
    })
    fenders_deployed: int = 0
    fenders_required: int = 2
    gangplank_deployed: bool = False
```

- **Fenders must be deployed before hull contact**; failure to prepare may result in damage to the vessel.
- **Lines are secured one at a time by sailors** (Part E tasks). A spring line first, then bow/stern lines. The ship is **not secure** until at least `bow_spring` and `stern_spring` are true.
- The **dock-holding feature** (if modelled) is explicitly **temporary stabilization only** — it does not prevent all movement and is not a substitute for lines.

### Phase 3 — Gangplank

```python
def deploy_gangplank(ctx) -> bool:
    if not all(ctx.mooring.lines[k] for k in ("bow_spring", "stern_spring")):
        return False                     # cannot rig a plank on an insecure ship
    if ctx.sea_state > 3:
        return False                     # too much movement at the rail
    ctx.mooring.gangplank_deployed = True
    return True
```

**No autoshore.** The player (or an officer) must explicitly order `deploy_gangplank`. Sailors can only leave the ship via the gangplank or a tender — **not** by walking off a moored hull. This is the "no auto shore, auto action" requirement, enforced structurally: shore access is gated on a physical object existing.

## I2. Autodock is assisted, not autonomous

Following the pattern of real assisted-docking systems: **the captain remains responsible and must be at or near the helm, attentive, and ready to take manual control**. In game terms:

- Autodock **proposes** a plan (approach vector, anchor drop point, line order, fender count).
- The player **confirms** each phase, or overrides.
- If the player is not at the helm (Part E task `helm` assigned to an NPC), autodock **degrades**: slower approach, higher chance of a fender miss, longer mooring time.

This keeps the simulation honest: the ship docks because someone is doing it, not because a menu button said so.

## I3. Failure modes

| Failure | Cause | Consequence |
|---|---|---|
| Hull contact | fenders < required at contact | hull damage, repair cost at next port |
| Line parted | mooring in sea_state > 3 without spring lines first | ship drifts, must re-anchor |
| Gangplank refused | lines not secure, or sea_state > 3 | shore access blocked until resolved |
| Anchor drag at mooring | poor holding ground, scope < 6:0 | ship swings into another berth or the quay |

## I4. Tests

| Test | Assertion |
|---|---|
| `test_fenders_before_contact` | 0 fenders at contact → hull damage event |
| `test_spring_lines_first` | bow/stern lines without springs → mooring not secure |
| `test_gangplank_requires_security` | lines incomplete → `deploy_gangplank` returns False |
| `test_gangplank_requires_calm` | sea_state 5 → returns False even with lines |
| `test_no_autoshore` | sailor cannot transition to shore state without gangplank |
| `test_autodock_requires_helm_attention` | no helm task assigned → autodock slower / higher failure |

# Part J — Longline Handling: Starboard Haul, Stern Set

**Module:** `fishing_sim/systems/longline.py`

## J1. What actually happens on deck

The real layout is specific and asymmetric:

- The **working deck is generally closed on the port side and open on the starboard side** — the line is hauled back on the **starboard side**, and fish are landed there.
- The **longline is set from the stern**, where branch lines and buoy lines are attached during setting.
- The **line hauler is positioned on the starboard side**, forward on the working deck, with a landing door just aft of it.
- The line can extend from **20 km to over 120 km**.
- Setting speed is around **8 knots** toward the desired location, with the downline and first weights deployed first.

So the ship is **not symmetrical in its fishing gear**, and the sim should reflect that:

```python
LONGLINE_LAYOUT = {
    "haul_side": "starboard",
    "set_point": "stern",
    "hauler_station": Vec2(x=+2.4, y=-3.1),    # starboard, forward
    "landing_door": Vec2(x=+2.4, y=-4.0),      # starboard, aft of hauler
    "port_side": "closed",                      # rail / bulwark
    "branch_line_length_m": (30.0, 50.0),       # typical range
    "mainline_length_km": (20.0, 120.0),
    "set_speed_kn": 8.0,
}
```

## J2. Setting vs hauling as distinct states

```python
@dataclass
class LonglineState:
    phase: str = "stowed"              # stowed | setting | set | hauling | stowed
    mainline_out_m: float = 0.0
    hooks_set: int = 0
    hooks_hauled: int = 0
    set_started: float = 0.0
    haul_started: float = 0.0
    fouled: bool = False               # Part C/D fouling
```

- **Setting**: ship steams at ~8 kn on the chosen course; crew attach branch lines at the stern; the line pays out. **Ship speed and heading are part of the fishing operation**, not just transit.
- **Hauling**: ship is **stopped or nearly stopped**; the starboard hauler pulls the line in; fish are landed at the starboard landing door; crew process and stow.
- **Collision relevance**: because hauling is **starboard-only**, the ship's **port side is the working side for other traffic** during hauling — other vessels can pass to port without interfering with gear. This is a real operational reason for the asymmetry, and it makes the traffic system (Part earlier) interact with fishing in a meaningful way.

## J3. Collision consequences for gear

You mentioned collisions are now in the sim. Apply them to the longline explicitly:

```python
def longline_collision_check(state, ship, other_vessel, ctx):
    if state.phase not in ("set", "hauling"):
        return
    # mainline runs astern / to starboard of the ship
    if mainline_intersects(other_vessel.path, state, ctx):
        state.fouled = True
        emit_event("gear_collision", other_vessel.id)
```

Consequences:

- `fouled = True` → hauling stalls, **crew task `clear_gear`** required (Part C/E).
- If the other vessel's prop is involved, the line **parts** — `mainline_out_m` drops, `hooks_lost` increments, and the economic loss is real.
- The other vessel may not even notice; the game logs it as an incident for the captain's report.

## J4. Starboard-side tasks

| Task | Station | Notes |
|---|---|---|
| `set_line` | stern | ship must be at set speed |
| `haul_line` | starboard hauler | ship must be near-stopped |
| `land_fish` | starboard landing door | after hauling |
| `bait_hooks` | stern / bait table | during setting |
| `clear_gear` | wherever fouled | Part C/E |

Because these stations are **on the starboard side**, a sailor assigned to `haul_line` walks a different path than one assigned to `helm`, and the bottleneck system (Part B3) makes the starboard deck genuinely crowded during hauling.

## Known limitations

- **Hypothermia has no medical treatment** in this slice. Serious cases hand off to the existing medical/rescue hook, same as Part D's overboard.
- **Watch rotation is data-driven but not negotiable.** A future slice could let the captain adjust the watch bill, with trust/fatigue consequences.
- **Bird sighting spawn is density-based, not a full ecosystem.** It does not track individual schools; it tracks where fish *are likely to be*, and birds are the visible signal.

- **No SFX** — consistent with the earlier slice. All new events carry a `category` so audio can be added later without touching this code.
# Part K — The Sale: Buyers, Bar Graph, and Personality

**Module:** `fishing_sim/systems/market.py`
**New entity:** `Buyer` (per port, per seed — see Part O)

## K1. The shape of a sale

Selling a catch is **not a menu**. It's a timed negotiation between the captain and 2–5 buyers at the quay, each with their own wants, patience, and budget. The player either **picks a buyer** for the whole lot or **autosells** under pre-set rules.

The bar graph is the **visible state of that negotiation** — every buyer's current offer, drawn as a bar, rising or falling as time passes and competitors move.

## K2. Buyer entity

```python
@dataclass
class Buyer:
    id: str
    name: str                                # "Halvorsen & Sons", "The Ice Queen"
    business: str                            # port-side business id (Part O)
    personality: BuyerPersonality
    base_price_index: float                  # 0.7..1.4, per-buyer baseline
    species_weights: dict[str, float]        # relative preference
    patience: float                          # seconds until they walk
    budget_kg: float                         # max they can take this visit
    mood: float = 1.0                        # 0.5..1.5, drifts
    trust: float = 0.0                       # -1..1, relationship with captain (K5)

@dataclass
class BuyerPersonality:
    aggression: float          # 0..1, how fast offers move
    risk: float                # 0..1, willingness to bid above true max
    specialty: str             # "tuna" | "general" | "gourmet" | "bulk"
    honesty: float             # 0..1, how close displayed price is to true max
    drift_bias: float          # -1..1, which way their bar tends to drift
```

## K3. Offer math

Every `OFFER_TICK` (default 0.5 s), each buyer recomputes their **displayed offer**:

```python
def compute_offer(buyer, lot, ctx) -> float:
    base = ctx.market_price(lot.species) * buyer.base_price_index
    pref = buyer.species_weights.get(lot.species, 1.0)
    mood = buyer.mood
    trust_bonus = 1.0 + 0.15 * buyer.trust          # trusted buyers pay more
    volume_pen = max(0.5, 1.0 - 0.3 * (lot.kg / buyer.budget_kg))

    target = base * pref * mood * trust_bonus * volume_pen
    return target
```

The **displayed offer** is what the bar shows. The **true offer** is what the player actually gets if they accept — and they can differ if `honesty < 1` (see K4).

## K4. The bar graph

The bar graph has one bar per buyer:

```
HALVORSEN & SONS      $4.20/kg   [██████████████        ]  ^
THE ICE QUEEN         $3.85/kg   [███████████           ]  v
DOCK 7 CO-OP          $4.05/kg   [█████████████         ]  -
```

Each bar encodes three things:

| Element | Meaning |
|---|---|
| Bar fill | Offer as fraction of the current best offer (best = full bar) |
| Arrow | Trend over the last 5 s (up / down / flat) |
| Fill colour | Buyer mood: green (happy) → amber (impatient) → red (walking) |

**The bar graph is the negotiation.** The player watches the bars move and decides:

- **Accept now** (click buyer) → executed at **displayed** price × honesty.
- **Wait** → bars keep moving; a buyer may walk when `patience` hits 0.
- **Autosell** → pre-configured rules run automatically (K6).

### K4.1 Why the bars move

Offers move for four reasons:

1. **Competitor pressure** — if buyer A is currently highest, buyers B and C shift their offers *toward* A's (they don't want to be undercut) at a rate scaled by `aggression`.
2. **Mood drift** — every buyer's `mood` drifts ±0.02 per offer tick in the direction of `drift_bias`. A buyer who trends up will eventually stop trending up and start trending down; this is the tension.
3. **Patience decay** — as `patience` falls, the buyer's `mood` drops faster. A buyer at 30% patience is cheap; at 5% they're on the edge of walking, and their offer is *lower* than at their peak.
4. **Lot freshness** — the longer the catch sits on the quay, the more the whole market degrades (`market_price` × `0.98` per 10 min). Waiting is not free.

So the skill is **reading the bars**: is buyer A's offer trending up because they want it, or because they're the only one who hasn't dropped yet? Is buyer C about to walk (patience bar shortening) and let A and B fight it out — or will A and B *also* drop the moment C leaves?

## K5. Trust and relationship per buyer

Every completed sale updates `buyer.trust`:

| Event | Update |
|---|---|
| Player accepts buyer's offer | `trust += 0.05` |
| Player accepts while buyer is the **best** offer | `trust += 0.02` extra |
| Player accepts while buyer is the **worst** offer (bad faith) | `trust -= 0.10` |
| Player holds out past `patience * 0.85` then sells to this buyer | `trust -= 0.03` (they know you were haggling) |
| Player lets buyer walk (patience → 0, never accepted) | `trust -= 0.15` |
| Buyer gets a **repeat** purchase within 3 in-game days | `trust += 0.08` |
| Buyer sees a better species come back later | `trust += 0.02` (they remember quality) |

**Trust effects**:

- **Displayed price** — the `trust_bonus` term above. A trusted buyer shows you their real offer.
- **Honesty** — `effective_honesty = honesty + 0.3 * trust`. Untrusted buyers lowball. Trusted buyers don't.
- **Patience** — a trusted buyer waits 20% longer before walking.
- **Reveal** — a trusted buyer will show their **true max price** for a lot (a small `max` marker on the bar). Untrusted buyers hide it.
- **Repeat visits** — a high-trust buyer will **come to the ship** for first pick of the next catch. This is a "visit offer" event (K7).

Trust decays slowly (`-0.005/s` if not transacted with in 5 in-game days) — relationships don't last forever.

## K6. Autosell rules

Autosell is **rule-based**, not magic. The player sets:

```python
@dataclass
class AutosellRule:
    enabled: bool = True
    min_price_fraction: float = 0.85     # sell if offer >= 85% of best-so-far
    preferred_buyers: list[str] = []     # priority order
    max_wait_s: float = 90.0             # give up and take best at this point
    species_restrictions: dict[str, str] = {}  # "tuna" -> "only_the_ice_queen"
```

Rules fire when **all** conditions hold for a given buyer:

```python
def should_autosell(rule, buyer, best_offer_so_far, elapsed_s):
    if rule.preferred_buyers and buyer.id not in rule.preferred_buyers:
        return False
    if buyer.offer < rule.min_price_fraction * best_offer_so_far:
        return False
    if elapsed_s > rule.max_wait_s and buyer.offer < 0.95 * best_offer_so_far:
        return False
    return True
```

**Autosell is not free money.** It gives up the possibility of a walk-away-beats-everything moment, and it **erodes trust** with buyers who want to be personally selected — autosell always applies the "worst offer accepted" penalty to non-preferred buyers. That's the tax on not negotiating.

## K7. The "visit" event

When `trust > 0.6` with a buyer and the ship next docks, the buyer **visits the ship** before the market opens. They see the catch first, make a **single fixed offer** (typically 1.10× their normal high), and the player can accept immediately or decline and take their chances at the quay.

- **Accept**: `trust += 0.05`, no market negotiation, quality premium.
- **Decline**: `trust -= 0.10`, buyer doesn't visit again for 2 visits, and their next market offer is 5% lower.

This is the relationship payoff — **first pick** is worth something concrete.

## K8. Species and specialisation

Buyers aren't interchangeable. A buyer with `specialty: "gourmet"` pays 1.5× for the **top 20% by quality** of a lot and 0.6× for the rest. A `bulk` buyer pays 0.9× across the board but takes *everything*, no minimum quality. A `tuna` specialist may refuse a mixed lot entirely if the tuna fraction is below 30%.

So "choose each buyer" is genuinely a decision, not a click:

- **Gourmet** for the top-quality subset (split the lot — see K9).
- **Bulk** for the tail (low quality, fast exit, low trust).
- **Specialist** when the species matches, but only if the lot is mostly that species.

## K9. Lot splitting (advanced, but supported)

The player can **split the catch** across two buyers in one session:

- Sell the top 25% to the gourmet (1.5× price).
- Sell the tail to the bulk buyer (0.9× price, accepts quality floor).
- Net effect is often better than either buyer alone — **if** trust is high enough that the gourmet doesn't refuse the split.

Split sales apply half the trust gain to each buyer (they each want the whole thing).

# Part P — Harness: The Tether That Actually Saves You

**Module:** `fishing_sim/systems/harness.py`
**Requires:** `jacklines_fitted` upgrade (Part O) for full functionality; basic harness usable without.

## P1. What a real safety harness does

On commercial fishing vessels, a **safety harness with a tether clipped to a jackline or fixed point** is the standard defence against going overboard. When worn and tethered, a sailor who slips and slides toward the rail is **stopped by the tether** — they may be dragged, injured, or half-dragged over the rail, but they don't enter the water. This has saved lives repeatedly.

But it has real costs and dangers:

- **Tethered sailors can drown** if dragged over and held under — the tether becomes a trap.
- **Tether snags** on deck fittings; a tethered sailor can be caught on a cleat and unable to move.
- **Clipping in and out takes time** — a sailor on a moving deck may skip the clip-out to save seconds.
- **Tethered sailors can't easily reach a rail to catch someone else** — the tether limits their reach.
- **Ladders and hatches** require clip-out and re-clip — the transition is the danger window.

The harness is a **rich mechanical system**, not a button that says "safe".

## P2. State

```python
@dataclass
class HarnessState:
    worn: bool = False             # is the harness on the body
    tethered_to: str | None = None # jackline id, fixed point id, or None
    tether_length_m: float = 2.0
    clip_in_time: float = 0.0      # seconds remaining to complete clip
    clip_out_time: float = 0.0
    snagged: bool = False
    snag_point: Vec2 | None = None
    dragged_since: float | None = None  # if being dragged by tether
```

## P3. The mechanical effects

### P3.1 While tethered

- **Overboard is prevented** (no transition to `mode="overboard"` from Part D5).
- **Slip and slide still happen** (Part C) — the sailor is dragged to the end of their tether, but doesn't go in.
- **Dragged state**: if `slide_vel > 2.0` when the tether pulls taut, the sailor is `dragged` — a new motion state where they're pulled along the deck at the tether end. They may:
  - **hit an obstruction** (winch, cleat, hatch coaming) → `injured` (Part C6's injury system), `dragged_since` continues.
  - **be pulled over the rail and held under the surface** — this is the real danger. Probability of `dragged_over_rail` scales with `slide_vel` and proximity to the rail at tether end.
- **Dragged over rail and held under**: if a rescuer (Part D4) **cuts the tether** within a window (default 8 s), the sailor is **unconscious but recoverable**. If not cut, the sailor is **lost** — a real death, not a stumble. This is the one place the sim should permit loss.
- **The tether can be cut** by a rescuer in `catch_attempt` mode or by the player if in range. Cutting is a **deliberate, irreversible action**, not a menu toggle.

### P3.2 While untethered (but harness worn)

- **No overboard prevention** — the tether is what saves you, not the harness.
- **Falls still occur** (Part C) — the harness does nothing for footing.
- The harness *worn but not clipped* is the worst state: the sailor thinks they're safe, and isn't. **This is the lie the sim teaches** — and the reason `clip_in_time` matters.

### P3.3 Clip transitions

Entering or leaving a tethered zone takes time:

| Transition | Base time | If rushed |
|---|---|---|
| Clip in | 2.0 s | 0.5 s if `rushed=True` (Part C: clip-in is interrupted if a slip occurs during the 0.5 s, and the tether fails) |
| Clip out | 1.5 s | 0.3 s if rushed (same failure risk) |
| Ladder transition | clip out + clip in sequence | 4.0 s total, or 0.8 s rushed with failure risk |

**A sailor crossing a ladder is untethered for the duration.** In a storm, this is the moment where they go in. This is not punitive; it is the real risk.

## P4. Where the tether attaches

Jacklines run along the deck (from the `jacklines_fitted` upgrade, Part O). Fixed points exist at the helm, hatch, winch, and haul stations. A sailor can clip to:

```python
TETHER_POINTS = [
    # id, type, position (ship-local), usable_by
    ("jackline_port", "jackline", ...),
    ("jackline_stbd", "jackline", ...),
    ("helm_fixed", "fixed", ...),
    ("hatch_coaming", "fixed", ...),
    ("hauler_fixed", "fixed", ...),
]
```

**Fixed points don't allow much movement** — a sailor clipped to the helm can only work the helm. **Jacklines allow walking the deck**, but the tether can snag on obstacles.

Snag probability per meter of movement while tethered:

```python
def snag_probability(distance_m, deck_clutter, tether_condition):
    return 0.004 * distance_m * deck_clutter / max(0.5, tether_condition)
```

`deck_clutter` comes from Part C's `DeckRegion.clutter`. A cluttered deck snags tethers. **Wash-down and tidy-up (Part C's counterplay) directly serve the harness system** — an unkempt deck is dangerous not just for slips, but for the tether.

## P5. When do sailors wear it?

The harness is **the captain's decision** (or the officer's):

```python
HARNESS_POLICY = {
    "never": 0,          # never worn
    "storm": 1,          # worn when sea_state >= 4 or wind >= 20 kn
    "always": 2,         # worn on deck at all times
    "custom": 3,         # player-defined conditions
}
```

**Crew resistance**: sailors find the harness hot, restrictive, and slow. A crew with low trust (Parts D7, K5) may **skip clipping in** — a per-sailor `compliance` probability scaled by trust and fatigue. A tired, resentful crew tethers *sometimes*, which is worse than not at all — because they think they're safe.

```python
def tether_compliance_probability(sailor, ctx):
    p = 0.9
    p -= 0.3 * (1.0 - sailor.trust_captain)     # distrust → skip
    p -= 0.2 * sailor.fatigue                    # tired → skip
    p -= 0.1 * (1.0 if ctx.rushed else 0.0)      # rushing → skip
    return clamp(p, 0.1, 0.99)
```

**This is the point of trust mattering.** A captain who ignores crew welfare gets a crew that doesn't clip in.

## P6. What the harness is *not* — and why that matters

The harness does **not**:

- Prevent slips (Part C — nothing does).
- Prevent being dragged (Part P3.1 — it makes it worse, if anything).
- Make a sailor immune to cold (Part E — hypothermia still climbs).
- Guarantee recovery if they go over.

It is a **tether with teeth**: it stops the fall, but creates new dangers and demands discipline. The player feels this most when they see a sailor being dragged toward the rail — tether taut, hand reaching for a cleat — and have to decide whether to cut it or trust the line.

## P7. Interaction with Parts C, D, E, F

| Part | Interaction |
|---|---|
| **C (slip/trip)** | Slips still happen; slide is arrested at tether end (drag state) |
| **D (overboard/alarm)** | Tethered sailors don't transition to `overboard`; but `dragged_over_rail` is a *separate* outcome that triggers the same MOB alarm chain — a rescuer must cut the tether |
| **D (catch attempt)** | A rescuer cannot catch a **tethered** sailor at full reach (tether is in the way); catch probability −0.2 unless the rescuer is untethered |
| **E (work/rest)** | Wearing the harness all day adds `fatigue +0.05/hour`; nobody wears it in quarters |
| **F (bird sighting)** | A tethered lookout sees the birds but their movement is limited to the tether arc; a **fixed-point** lookout misses birds outside their cone |
| **G (voyage decision)** | Tethered is the *default* in heavy weather; the sim assumes harnesses worn when `sea_state >= 5` unless the captain has explicitly forbidden it |

## Integration order (Parts K–P appended to the master order)

The Parts E–J list ended with longline. The K–P additions slot in like this:

1. **Part N (naming + seed)** — must come first; everything downstream references ship name, captain name, and seed-derived world.
2. **Part O (upgrades)** — depends on N for shipyard ports, and unlocks Q (harness requires jacklines).
3. **Part L (logs)** — depends on N for the ship/captain names it records.
4. **Part M (notebook/export)** — depends on L for the streams it exports.
5. **Part K (buyers + bar graph)** — depends on N for the seeded buyer roster, and on L for the ship log recording sales.
6. **Part P (harness)** — depends on O (`jacklines_fitted`), C (slip physics), and D (overboard/rescue).
7. **Part Q (the minigame for sale action)** — if implemented as a *separate* interactive minigame beyond the bar graph (see §Limitations), it would come after K.

## Known limitations

- **The bar graph is the negotiation.** There is no separate "action minigame" beyond watching the bars and clicking a buyer. If the design intent is a *physical* minigame (e.g. a timing challenge to place an order before a bar collapses), that is a distinct slice — this doc deliberately keeps the negotiation **strategic, not reflex**. Note this explicitly.
- **Buyers do not know each other's offers.** They react to the *visible best offer* — realistic enough, but not a full auction model. Fine for this scope.
- **Captain's log is partially auto-generated.** The player *can* type into it, but auto-lines are generated for major events so the log isn't empty. A stricter "player writes every line" mode is a one-line config flag.
- **Nav log is 15-minute fixes by default.** A player can set 5-minute fixes for higher resolution at the cost of larger exported files.
- **Seed world is finite.** 3–5 ports, 2–4 businesses each, 6–8 sailor candidates. A larger world is a Phase B pass; the current scope is a **voyage**, not a world.
- **Upgrades are fixed-catalogue.** No procedural upgrades. A future slice could generate shipyard offers from a recipe list; this one is hand-authored.
- **Harness death is the only death in the sim.** Everything else is injury or rest. The `lost` outcome is deliberately narrow: dragged over rail + tether not cut in time. This is the one place the sim permits loss, and it should be rare enough to feel like a real tragedy, not a gameplay failure.
- **No SFX.** Same as before. The tether **snap** is the most impactful missing sound; `VocalEvent`-style hooks exist for it (`tether_snap`, `dragged`, `cut`), the audio layer is future.
